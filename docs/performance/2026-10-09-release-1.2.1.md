# niraNG 1.2.1 publication follow-up

## Scope

Publish the approved Android refinements as 1.2.1+23, native code 4023. Keep Windows and pending PHP/server changes out of the release commit. No app launch, uninstall, cache clearing, intermediate historical installation or live service test on the user's phone.

- Replace the separated bottom navigation / system safe-area materials with one rim-free FrostedSurface. NavigationBar's own SafeArea still positions app controls above Android buttons; the same material continues behind transparent system navigation. Divider and Android contrast enforcement remain disabled. The rest of the Liquid Glass UI is unchanged.
- Connect, Disconnect and Restart share a monotonic 500ms minimum accepted-start interval. Existing per-key single-flight and 500ms post-completion cooldown remain. Ignored taps do not replay feedback or enter a queue. A pending Connect does not indefinitely lock Disconnect: cancellation can be accepted after the shared interval.

## Upgrade review

Local historical APKs were matched against GitHub's published SHA-256 digests for all three ABIs in 1.1.9 and 1.2.0. All six use package `dev.nirang.client` and signing certificate SHA-256 `290bd5c9aebb9bf0cc4933f26fcc8ca2712cc65c113bfce99ff5c769598545c4`.

- 1.1.9 installation codes: ARM32 1021, ARM64 2021, x86-64 4021.
- 1.2.0 installation codes: 4022 for every architecture.
- 1.2.1 installation codes: 4023 for every architecture, including universal.

No data format or preference namespace changes in this follow-up. NativeSettings fills only missing defaults and recognizes existing state. SubscriptionRepository reuses the same cache path, saved selection/order and profile overrides; SecureSubscriptionCache retains its envelope/key alias and recognizes older plaintext files. DeviceRegistrationManager reuses saved installation ID / first-seen. Those paths do not depend on having installed intermediate experimental 1.2.1 builds. Upgrade packaging and source compatibility are checked, not a new physical-device migration from every historical release or an all-device no-lag guarantee.

## Installation / policy findings

The merged release APK requests network, foreground VPN service, notification and user-initiated APK-updater permissions, plus WorkManager's wake-lock / boot-completed support and its internal non-exported receiver permission. It does not declare SMS reading, accessibility, notification-listener or device-administration access. VPN consent comes from VpnService.prepare; notification permission is requested for service status. UpdateInstaller opens the system installer after downloading/verifying the APK, not silent installation.

Google distinguishes unfamiliar sideloaded APK scan prompts from harmful-app classifications and runtime permission dialogs. Signing an APK does not exempt it from Play Protect. No protection is disabled or bypassed here. A specific harmful-app warning needs its exact text and a separate review/appeal, not a promise that a code change removes it.

References checked on 2026-10-09:

- https://developers.google.com/android/play-protect/warning-dev-guidance
- https://developer.android.com/developer-verification

The current developer-verification rollout describes selected participating stores/regions from 2026-09-30 and wider rollout in 2027; this is separate from the ordinary request to scan an unknown APK. Developer-account registration or policy appeals were not performed.
